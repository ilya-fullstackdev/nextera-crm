## Функционал

### Главная

Персональная сводка при входе: новые лиды за сегодня, задачи на сегодня и просроченные, количество лидов в работе, счётчик переданных руководителю. Ниже — последние лиды, ближайшие задачи и лента последней активности по команде. У руководителя сводка показывает данные по всем сотрудникам, у остальных — только по своим.

### Лиды

Таблица лидов с компанией, контактом, должностью, статусом, приоритетом, ответственным, датой следующего контакта, источником и последней активностью. Поиск по компании/контакту/телефону, фильтры по статусу, приоритету, ответственному, источнику, а также быстрые переключатели «Контакт сегодня» и «Без сайта». По правому клику на строке — быстрая смена приоритета и удаление (только у руководителя). На мобильных — карточный вид с быстрым звонком в один тап.

При создании лида система сама проверяет возможные дубли — по названию компании, домену сайта и телефону — и показывает похожие карточки, прежде чем завести новую.

### Карточка лида

- **Быстрые действия** — позвонить, написать в Telegram, добавить задачу или активность, отредактировать, передать лид, оформить отказ.
- **История** — единая лента активности: звонки, сообщения, письма, встречи, заметки, смены статуса, передачи и отказы, с указанием автора и времени.
- **Задачи** — чек-лист задач по лиду с отметкой «выполнено».
- **Файлы** — загрузка и хранение документов (КП, брифы, ТЗ, договоры) с категорией, размером и автором.
- **Квалификация** — статус ЛПР, уровень потребности, проблема, желаемый результат, сроки сделки, статус и комментарий по бюджету, уровень заинтересованности, текущий подрядчик — сохраняется автоматически при изменении поля.
- **Лица, принимающие решение** — привязка существующих контактов компании или добавление новых.

### Что происходит само

Рутину CRM берёт на себя:

- **Задача ставится сразу.** Как только человек завёл лид, у него в задачах появляется «Позвонить: Компания» на сегодня — ответственным записан тот, кто лид добавил. Телефон контакта подставляется в комментарий.
- **Статус двигается сам** по мере заполнения карточки, вручную переключать стадию не нужно:

  | Что сделали | Куда переходит лид |
  |---|---|
  | Появилась первая заметка, файл или активность | Поиск ЛПР |
  | Записали звонок, сообщение, письмо или встречу | Первый контакт |
  | Отметили, что ЛПР найден, или добавили участника | ЛПР найден |
  | Плюс указали потребность и бюджет либо сроки | Квалификация |

  Автоматика работает только вперёд и никогда не откатывает статус назад. Дальше квалификации лид двигают руками: передача, отказ, переговоры и сделка — решения человека, а не следствие заполненного поля. Лид на паузе («Перезвонить позже») и уже переданный руководителю автоматика не трогает. Каждый автопереход пишется в историю лида, и на экране всплывает подсказка «Лид перешёл на следующий этап».
- **Подсказка «что делать дальше».** В карточке лида блок «Следующий шаг» меняется по мере заполнения: «Позвонить и записать результат» → «Выйти на ЛПР» → «Выяснить потребность» → «Уточнить бюджет и сроки» → «Передать лид руководителю». Рядом — кнопка, которая сразу открывает нужное окно, и пояснение, что произойдёт после.
- **Задача при передаче.** Тому, кто получил лид, автоматически ставится задача связаться с клиентом на следующий день.
- **Задача на повторный контакт.** Если при записи активности указать дату следующего контакта, задача создастся сама.

### Воронка

Канбан-доска по стадиям сделки (от «Новый» до «Сделка»/«Отказ») с перетаскиванием карточек между колонками. Карточка показывает компанию, контакт, приоритет, ответственного и дату следующего контакта. Перенос в «Отказ» или «Передан руководителю» выполняется только через соответствующие модальные окна с обязательным заполнением причины/данных передачи — так в базе не остаётся сделок без объяснения смены статуса.

### Передача лида

Оператор оформляет передачу лида через форму брифинга: статус ЛПР, суть потребности, ситуация клиента, проблема, желаемый результат, сроки, бюджет, что обсуждалось, возражения, следующий шаг. Лид принимает руководитель — отдельной должности менеджера в структуре нет. При сохранении лид переходит в статус «Передан руководителю», меняется ответственный, и новому владельцу автоматически ставится задача связаться с клиентом на следующий день.

### Закрытие сделки (только руководитель)

На карточке лида руководитель нажимает «Закрыть сделку» и указывает сумму, которую заплатили за работу, проценты исполнителям и ежемесячные расходы проекта (хостинг, домен, почта — со ссылками). Окно сразу показывает, сколько уйдёт людям и сколько останется студии. Лид переходит в статус «Сделка», а выплаты и расходы появляются в соответствующих разделах.

### Отказы

Оформление отказа требует выбора причины из справочника (нет потребности, есть подрядчик, недавно делали сайт/редизайн, дорого, нет бюджета, не сейчас, выбрали другого, не удалось связаться с ЛПР, другое) и опционального комментария. Лид попадает в раздел «Отказы» с сохранением причины в истории.

### Задачи

Доска задач с вкладками «Просроченные», «Сегодня», «Предстоящие» и «Выполненные». Задача привязывается к лиду или создаётся как самостоятельная, отмечается выполненной одним кликом. Видны тип задачи, срок, связанный лид и исполнитель.

### Компании и контакты

Справочники компаний и контактов с карточками, поиском и переходом к связанным лидам — единая база вместо дублирования данных клиента в каждом лиде.

### Отчёты (только руководитель)

Выбор периода (сегодня/неделя/месяц/произвольный диапазон) и набор метрик: новые лиды, лиды в работе, найдено ЛПР, квалифицировано, передано руководителю, сделки, отказы — каждая плитка показывает долю от новых лидов периода. Воронка квалификации показывает, сколько лидов доходит до каждого шага и какая конверсия с предыдущего; рядом — динамика новых лидов по дням, распределение по стадиям, причины отказов с долями, эффективность источников (конверсия в сделку), нагрузка по сотрудникам и лента последних действий.

### Найм (отдел кадров)

У отдела кадров своя главная: состав отдела холодных звонков, сколько человек работает и сколько заблокировано, найм по месяцам за полгода, последние нанятые и список тех, кто ещё ни разу не заходил в CRM. Раздел «Сотрудники» для этой роли показывает только отдел холодных звонков и позволяет заводить операторов и совмещённую должность.

### Журнал аудита (только руководитель)

Каждое значимое действие — создание/изменение/удаление сотрудника, смена роли, блокировка, сброс пароля, создание и удаление лидов, смена статуса, передача, отказ, изменения компаний и контактов — пишется в журнал с указанием автора, времени и сути изменения на человеческом языке. Журнал фильтруется по типу сущности и имени сотрудника.

### Сотрудники (руководитель и отдел кадров)

Создание учётных записей (логин, пароль, роль, статус), редактирование, блокировка/разблокировка, сброс пароля с одноразовым показом нового значения. Удаление сотрудника, у которого есть активные лиды или незавершённые задачи, требует сначала выбрать коллегу, на которого всё будет переназначено.

### Глобальный поиск

Поле поиска в шапке ищет по лидам: названию и сайту компании, имени, телефону, Telegram и email контакта — с быстрым переходом к нужной карточке.

## Роли и права

| Роль | Доступ |
|---|---|
| Оператор | свои лиды, задачи, воронка, компании/контакты, передача лида, отказы |
| Отдел кадров | только найм в отдел холодных звонков. Лиды, компании и контакты недоступны |
| Кадры + холодные звонки | совмещение: свои лиды как у оператора плюс найм в отдел |
| Руководитель | полный доступ ко всем лидам и сотрудникам, отчёты, журнал аудита |

Отдел кадров (`HR`) не видит ни одного лида: разделы с клиентской базой скрыты в
меню, страницы редиректят на главную, а API отвечает `403`. Главная у этой роли
своя — про состав отдела и найм. Совмещённая должность (`HR_OPERATOR`) работает
с лидами как оператор и дополнительно ведёт найм.

Кадровик управляет только сотрудниками отдела холодных звонков — заводить и
менять руководителей и других кадровиков он не может, а в списке
сотрудников видит только свой отдел. Руководитель управляет всеми.

Все правила собраны в `src/lib/permissions.ts` (`canViewLeads`,
`canManageEmployees`, `assignableRoles`, `canReceiveHandover`) — и клиент, и
сервер спрашивают их, а не проверяют роль по месту.

Проверка роли выполняется дважды: на клиенте (скрытие пунктов меню/кнопок) и
обязательно на сервере — в каждом Server Component через `requireRole()` /
`requireLeadsAccess()` / `requireEmployeesAccess()` и в каждом API route через
`requireApiRole()` / `requireApiLeadsAccess()` / `requireApiEmployeesAccess()`.
Прямой вызов административного API оператором или кадровиком возвращает `403`.

## Телефоны и планшеты

Интерфейс рассчитан на работу с телефона: таблицы превращаются в карточки, фильтры прячутся в шторку, создание висит на плавающей кнопке. Разделы «Выплаты» и «Расходы», карточка лида, окно закрытия сделки и настройка процентов на узком экране перестраиваются в одну колонку — суммы и кнопки не наезжают друг на друга. На планшете карточка лида идёт одной колонкой, а с ширины ноутбука появляется правая колонка со справкой по компании.

## Стек

- Next.js 16 (App Router, TypeScript)
- Tailwind CSS v4 (design tokens в `src/app/globals.css`)
- PostgreSQL + Prisma 7 (driver adapter `@prisma/adapter-pg`)
- Аутентификация: httpOnly JWT-сессия (`jose`, 30 дней) + `bcryptjs` для хеширования паролей
- Иконки: `lucide-react`

UI-кит (`src/components/ui`) написан с нуля поверх Tailwind, без сторонних библиотек компонентов.

## Быстрый старт

```bash
# 1. Установить зависимости
npm install

# 2. Поднять PostgreSQL (локально уже установлен через Homebrew)
brew services start postgresql@16
createdb nextera_crm   # если база ещё не создана

# 3. Скопировать .env (уже создан для локальной разработки) и применить миграции
npx prisma migrate dev

# 4. Сгенерировать Prisma Client (обычно не нужно — уже сгенерирован)
npx prisma generate

# 5. Засеять демо-данные
npx prisma db seed

# 6. Запустить dev-сервер
npm run dev
```

Приложение будет доступно на http://localhost:3000.

## Деньги: сделки, выплаты, расходы

### Как считаются выплаты

Когда руководитель закрывает сделку и указывает сумму, процент получают двое:

1. **Тот, кто нашёл лид** — сотрудник, который завёл карточку.
2. **Тот, кто привёл его в отдел холодных звонков** — рекрутёр из поля «Кто привёл сотрудника» в карточке сотрудника.

**Проценты закреплены за должностью,** а не за сделкой: они задаются один раз в разделе «Выплаты» и одинаково применяются ко всем новым сделкам. При закрытии сделки их не спрашивают — окно только показывает, кому и сколько уйдёт.

| Должность | За свой лид | За приведённого сотрудника |
|---|---|---|
| Оператор | 10% | — не занимается наймом |
| Кадры + холодные звонки | 10% | 5% |
| Отдел кадров | — не ведёт лиды | 5% |

Проценты, которых у должности быть не может, недоступны и в интерфейсе, и на сервере: оператору нельзя назначить процент за приведённого сотрудника, а кадровику — за свой лид. Обе выплаты сразу получает только совмещённая должность «Кадры + холодные звонки». Руководитель сам себе выплату не начисляет.

Это значения по умолчанию, они меняются в разделе «Выплаты». Уже закрытые сделки при изменении ставок не пересчитываются.

Если лид нашёл сам руководитель — платить некому, и строка выплаты не создаётся. То же самое, если рекрутёра не указали, если рекрутёр и есть тот, кто нашёл лид, или если у должности стоит 0%.

Кадровик, заводя сотрудника, автоматически записывает найм на себя — дальше с каждой сделки этого сотрудника ему идёт процент. Руководитель может указать рекрутёра вручную.

### Вкладка «Выплаты»

Выплаты сгруппированы **по проектам**, а не общей кучей: по каждой закрытой сделке видно её сумму, дату и список — кому, за что (нашёл лид / привёл сотрудника), какой процент и сколько денег. Кнопка «Выплачено» помечает конкретную выплату; сверху — сколько всего нужно выплатить и сколько уже выплачено.

### Вкладка «Расходы»

Расходы ведутся по каждому проекту отдельно: хостинг, домен, SSL, почта, сервисы. У каждой позиции — сумма, периодичность (**раз в месяц** или **раз в год**), дата следующего продления и ссылка: кнопка «Открыть» ведёт прямо в панель хостинга или к регистратору. Годовые платежи приводятся к месяцу автоматически, поэтому итоги «в месяц» и «в год» считаются честно: домен за 1 800 ₽ в год показывается как 150 ₽ в месяц.

В окне закрытия сделки расходы добавляются кнопками-заготовками «Хостинг», «Домен», «Почта» — остаётся вписать сумму и ссылку. Домен по умолчанию сразу годовой.

Сумму сделки можно поправить позже (выплаты пересчитаются по тем же процентам), а ошибочно закрытую сделку — отменить. И то, и другое запрещено, если хотя бы одна выплата уже отмечена как выплаченная.

Все три раздела — сделки, выплаты и расходы — доступны только руководителю.

## Файлы

Загруженные файлы лидов (КП, брифы, ТЗ, договоры) хранятся на диске в
`public/uploads/leads/<leadId>/` (до 20 МБ на файл) и не коммитятся в git.

## Деплой и режим технических работ

На время выката новой версии домен отдаёт страницу «Ведутся технические
работы» вместо полуживого сайта. Заглушка работает на двух уровнях, чтобы
её было видно и пока идёт сборка, и в момент перезапуска процесса.

**1. Уровень приложения.** `src/proxy.ts` перед любой другой логикой
проверяет режим техработ и отдаёт `503` со страницей `public/maintenance.html`
(для `/api/*` — JSON с тем же кодом). Включается любым из двух способов:

- файл-флаг `.maintenance` в корне проекта — подхватывается на лету,
  перезапуск не нужен;
- переменная окружения `MAINTENANCE_MODE=1` — нужен перезапуск.

**2. Уровень nginx.** Пример конфига — `deploy/nginx-crm.conf`. Пока лежит
файл-флаг, nginx сразу возвращает `503` со статической страницей, не обращаясь
к Node. Тот же `error_page 502/503/504` срабатывает, если приложение упало или
ещё не поднялось после рестарта — то есть в те секунды, когда уровень
приложения физически не может ответить. Без этого блока во время
`next build` и перезапуска пользователь увидит ошибку шлюза.

### Выкат

```bash
# на сервере, из корня проекта
RESTART_CMD="pm2 restart nextera-crm --update-env" ./scripts/deploy.sh
```

Скрипт по шагам: включает заглушку → `git pull` → `npm ci` →
`prisma migrate deploy` → `npm run build` → перезапуск → ждёт, пока приложение
ответит → снимает заглушку. Если любой шаг упал, заглушка **остаётся
включённой**, и посетители не увидят сломанную версию.

Переменные: `RESTART_CMD` (команда перезапуска, по умолчанию pm2), `PORT`
(по умолчанию `3000`), `SKIP_GIT=1` (не делать `git pull`).

### Ручное управление

```bash
./scripts/maintenance.sh on      # включить заглушку
./scripts/maintenance.sh status  # проверить состояние
./scripts/maintenance.sh off     # выключить
```

### Посмотреть сайт при включённой заглушке

Задайте на сервере `MAINTENANCE_BYPASS_TOKEN=<секрет>` и откройте любой адрес
с `?maintenance_bypass=<секрет>` — токен сохранится в cookie на 12 часов, и
сайт будет доступен вам, пока остальные видят заглушку. Без заданного токена
обойти заглушку нельзя.

Обход работает только на уровне приложения. Если nginx настроен по
`deploy/nginx-crm.conf`, он режет трафик раньше — для проверки перед снятием
заглушки удалите файл-флаг и зайдите по `http://127.0.0.1:3000` с сервера.

### Текст заглушки

Правится в `public/maintenance.html` — это самодостаточный HTML без сборки,
внешних шрифтов и скриптов, поэтому он открывается, даже когда от приложения
не осталось ничего живого.

## Известные упрощения / точки для расширения

- Телефония и Telegram-интеграция подготовлены на уровне схемы данных
  (поля `phone`, `telegram`, `LeadActivity.type = CALL/MESSAGE`), но без
  реального подключения к внешним провайдерам — это первое, что стоит
  подключить следующим шагом (см. `src/lib/duplicates.ts` и раздел
  активности лида для точки расширения).
- Email-рассылка и хранение переписки не реализованы, только поле `email`
  у контакта и тип активности `EMAIL`.
